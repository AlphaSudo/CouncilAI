This is public-text continuation, not provider-state resumption. The [Token Factory chat-completion reference](https://docs.tokenfactory.nebius.com/api-reference/inference/create-chat-completion) documents messages as input and a combined reasoning/output completion limit; it does not document a stopped-generation resume handle. If a failed request spent all of its output on reasoning, that computation cannot be recovered through this feature. Input cache hits, if any, remain provider-reported observations rather than promised savings.

Generation policy `token-factory-generation/4` additionally appends the same **4,000 reasoning-token system instruction** to each of the four models' council requests, including review and explicit recovery. It asks the model to avoid redundant deliberation and move to its best supported answer within that reasoning budget, while preserving uncertainty and the required stage format. It explicitly excludes final-answer length from this reasoning budget. Existing question text, response envelopes, monetary bounds, review schemas and no-hidden-retry rules remain in effect. This is an instruction-level target, **not a hard provider-enforced limit**. The checked Token Factory completion API documents a shared reasoning-plus-answer maximum and effort settings; it does not document a separate numeric reasoning-token limit for these four models. No speculative budget field is sent, and `max_completion_tokens` is not lowered to 4,000. The full existing output reservation is still required because a model may exceed the instruction. Usage compares each newly requested budget against reported reasoning tokens, showing within-budget, overshoot, or unknown; chunk counts are never used to estimate compliance. Older attempts retain their original generation metadata and do not acquire a retrospective budget. The change was tested offline; no real model generation was dispatched to establish compliance or speed.

Council requests now collect streaming public answer chunks and the final provider usage event. The 90-second read timeout applies to an idle connection rather than the whole generation. Reply Usage now displays **request seconds** and **output tokens per second including reasoning**. They do not measure provider queue time or engine-only decode speed. While a Token Factory request runs, a one-second UI timer continues even if the provider has not returned public text. The measurements establish that the 30-second deadline can abort a request that would succeed and that substantial waiting persists with a smaller completion allowance and modest reported reasoning. Policy `token-factory-generation/6` restores a **90-second read inactivity timeout** for Lightning while keeping thinking enabled and the 4,000-token instruction. An active stream may take longer than 90 seconds in total.
